## 0. 一句话

滚轮与拖拽在本线的**键通道上早有等价路径且驱动已经在用**，缺的不是能力而是**覆盖**：这两类交互"有没有被测过"这件事，在 v1–v3 口径下答案是 0；要补只有三条路——**前台鼠标批**（不裂 sha、每次占用前台）、**给鼠标动作加物理通道**（裂 sha、且在可复现记账上有硬伤）、**接受键通道优先并把鼠标交互写成已知边界**（零成本、最诚实）。

## 3. 要补什么（什么场景键盘等价物不够用）

键盘等价物能回答"能不能到达目标"，不能回答下面这四件事——它们才是滚轮 / 拖拽**作为交互形态**的真实内容：

1. **连续量的物理性**：滚轮的方向、单格幅度、连续多格的累计位移、有没有惯性/回弹。键通道的 `Next` 是**离散翻页**（一次 9 行），它把"滚多少"这件事整个抹掉了。
2. **轨迹与落点**：拖拽的关键不是"选中了"，而是**起点抓得准不准**（抓在边上会不会脱手）、**轨迹中途经过什么**、**落点偏几个像素还算命中**。键盘路径把"轨迹"替换成了两次离散动作（选 + 落），轨迹这一维直接消失。
3. **动作中途的干扰适应**：`move` 类干扰在拖拽**进行中**发生时，驱动必须**重新抓帧、重算落点**——这是"实时应变"最真实的形态之一，键通道的两次离散动作天然测不到。八问里唯一被判定为"能"的那一问（滚完用新帧重找）就是这一类的弱化版。
4. **"键盘等价物不存在"的那些界面**：练习靶是我们自己造的，键盘路径是我们自己给的。真实桌面软件/网页里大量交互**只有**鼠标形态（画布、拖拽排序、按住拖选、地图式视口）。这一条不影响本线已有结论，但影响**这套口径的可移植性**（`REPORT.md` §7.3 第 5 项），属于"迟早要碰"的问题。

**八问的现状**（`STATE.md` §16.4 的逐条判定，此处只记状态、不抄数字）：滚轮四问 = **1 能 / 1 代码级一致 / 2 量不到**；拖拽四问 = **4 量不到**。也就是说，**六问量不到的原因不是驱动不会，而是没有一条不抢前台的通道能把鼠标动作送到 Tk**。

## 4. 三条方案

### 方案 A：前台鼠标批（不裂 sha）

**做法**：一行代码都不改。把 `t_rows` / `t_chips` 两个场景按**鼠标通道**跑成正式批——驱动在非 `--bg` 下本来就走 `self.wheel()` / `self.drag()`（`:2329` / `:2877` 的另一支），执行器用真 `SendInput`，靶子窗口显式 `-WindowStyle Normal` 起在交互桌面。

**代价**：
- **每次占用前台与指针**（本机是用户的工作机）⇒ 只能在"用户明确许可的时间窗"里跑，且必须**逐批串行、单窗口**；
- 跑测前后要各确认一次锁屏状态（`wait_until_unlocked()`），中途被打断要按 partial 记账；
- 结果**必须显式标注通道**（鼠标批与后台键通道批不可直接比，这是引用纪律第 3 条）。

**收益**：这两类交互第一次拿到**可引用的批次证据**（带 `scripts_sha`、口径版本、四件留档），八问里的"量不到"有机会变成实测答案。

**风险**：前台批在历史上被抢占过一次（批次 3 整批作废）⇒ 运行定式必须包含"先记前台是谁、跑完记前台有没有被改变"，并且**第一批只跑小量**（12–16 题）先看几何与时序是否稳。

### 方案 B：给鼠标动作加"物理通道"（裂 sha，一次解决）

**做法**：让 `--bg` 模式下的鼠标动作不再走 `PostMessage`，而是走真 `SendInput` + 焦点/前台交接（模仿 `o_key` 的后台交接思路），使后台批也能"点得动"。

**代价与硬伤**：
1. **它做不到真正的后台**：Tk 不收投递消息，真 `SendInput` 就必须移动真实指针、把目标窗口调到能接收输入的状态 ⇒ 它本质上是"**方案 A 的自动化版本**"，占用前台这件事**不会消失**；
2. **改动落在被测工件之外**：鼠标动作的后台分支属于**执行器**（`D:\DSH\dsh-vision-kit\actor`，端口 `:8731`），而本线的 `scripts_sha` 只覆盖沙箱里的三个文件 ⇒ 这条改动**进不了 sha 表**，"这批是谁跑的"将无法从留档里核对——这违反本线的记账纪律；
3. **两条路径的长期维护面翻倍**：键通道已经证明够用，#18 是覆盖缺口而不是缺陷 ⇒ 为一个覆盖问题引入第二条鼠标实现，收益与代价不成比例。

**结论**：**不推荐**。除非将来出现"必须在不占用前台的前提下产生真实鼠标事件"的需求（例如把这条线常态化跑在用户工作机上），那时它才值得作为一条独立设计重开。

### 方案 C：接受"键通道优先"，把鼠标交互写成已知边界（零成本）

**做法**：不新增批次、不改代码，把结论写清楚：本线的**能力覆盖**是"键通道上的滚动与拖放 + 鼠标通道上的离散点击"，**连续鼠标交互（滚轮轨迹、拖拽轨迹与落点精度）在 v0–v3 口径下没有被测过**，并且写明原因（Tk 忽略投递的鼠标消息 + 不抢前台的约束）。

**代价**：这一族在报告里永远停在"未覆盖"；引用者必须自己读边界句（`REPORT.md` §6.2 D 族 / §7.2 / §7.3）。

**收益**：诚实、零成本、与报告已有的边界写法一致；且**它和方案 A 不冲突**——C 是"默认口径"，A 是"要用一次就付一次代价"的窄用途。

## 5. 推荐

**推荐 C 作为默认口径；需要真凭据时用 A 跑一次窄批（12–16 题，两个场景各半）；B 暂不做。**

理由按顺序：

1. #18 是**覆盖缺口**（§2 已定案）——补它是为了"这两类交互测过"，不是为了修坏东西 ⇒ 不该为它引入长期维护面（B 的两条硬伤）。
2. **A 的边际收益最高、成本最低**：代码零改动、驱动两条路径本来就在，唯一要付的是"占用前台一个时间窗"，而这个时间窗是**可协商、可控制、可记账**的（写进 json 与引用行）。
3. **C 保证诚实**：即使一次 A 都不跑，"未覆盖"这件事也必须写在明面上；A 跑完也只是把这一族从"未覆盖"改成"已覆盖（鼠标通道、单批少量题）"，边界仍然要带。
4. B 被否的理由是**记账**而不是难度：一条进不了 `scripts_sha` 的改动，会让这条线的读数重新变得不可核对——这正是本项目最想避免的事。

## 7. 2026-10-05 第十五段：**方案选定**（决策；不改代码、不跑批、不裂 sha）

**决定：走 C（键通道优先 + 把鼠标连续交互写成已知边界）**；A 保留为"按需一次性窄批"；**B 不做**。本节只写决策与代价，不重复 §1–§6 的证据。

### 7.1 为什么是 C

- 滚轮与拖拽在 app 侧**都有完整的键盘等价物**（`Next`/`Prior`/`Up`/`Down`/`Home`/`End`、chips 的 `_bind_key`），**驱动已经在用**（§2）—— 缺的只是"**真实鼠标连续动作**"这一层，不是"这条交互测不了"。
- 键通道能回答的是"视口/轨迹类交互**在键通道下**能不能完成"，这在本线口径内是有效覆盖；真正缺的是"连续动作的物理性 / 轨迹与落点精度 / 中途 `move` 干扰适应"这类**只有真鼠标才能回答**的问题（§3 的四件事）。
- 与 #20 同一条纪律：**改动落在被测工件之外（actor）就不做** —— 本节的 B 与 `STATE.md` §24 的 B 是**同根否决**。

### 7.2 C 的代价（写清楚，不粉饰）

- **滚轮 / 拖拽的真实鼠标路径永远不被自动化测试覆盖**：`stats.drags > 0` 的批次永远为零，`stats.scrolls` 同理；任何"连续动作精度 / 中途干扰适应"的问题只能靠**前台手工验证**（人点人拖、看靶子行为），**不能写进成绩**。
- 报告与 `HANDOFF.md` 必须**显式**写这句（盲区 21 + `REPORT.md` §6.2 D 族 / §7.2），否则读者会把"**没测**"误读成"**测了没问题**"。
- 账目上：#18 **保持开着**（"欠（有据）"），不改成"已关闭" —— C 是"把边界写清"，不是"把欠账划掉"。

### 7.3 A 的唯一适用场景

- 当外部（报告读者 / 评审）要求"鼠标连续交互"的**真凭据**时，跑一次**窄批**：`t_rows` + `t_chips` 各 6–8 题、**前台**、单批、显式声明通道与前台占用，产出带 `scripts_sha` 的记录。
- 判据沿用 §6 的"**A 部分成立**"分支：跑到的问有实测答案 ⇒ #18 从"欠（有据）"改成"**部分覆盖（鼠标通道、单批少量题）**"；**不改口径版本、不进定稿线**。

### 7.4 B 不做的完整理由

- 改动落在 `D:\DSH\dsh-vision-kit\actor`（执行器侧）：`scripts_sha` 只覆盖 `../sol/sandbox` 三件套 ⇒ 以此跑出的读数**在留档里不可核对**（第十段 #16 的根因就在 actor 侧）。
- actor 的 `_maybe_front()` 是**鼠标与按键两种 op 共用**的输入前处理（逐字："raise (and pin) the target first, so DSH stealing the foreground cannot eat the keystrokes"）：改它等于改所有输入 op 的语义，且**必然要动前台** ⇒ 与本线 `--bg` 通道"不抢前台"的性质冲突。
- 即便改成功，收益也只是"把一条**已被键通道覆盖**的能力搬到鼠标通道上再测一遍" ⇒ 边际收益低，代价却是动全机共用的常驻件。

### 8.1 actor 能力（**结论：不用改 actor**）

| 问题 | 证据 | 结论 |
|---|---|---|
| actor 能发滚轮事件吗？ | 模块 docstring 的 `Ops:` 行里 **`scroll` 是一等 op**（`@op('scroll')`）；`post_scroll()` 的 docstring「Post wheel messages. dy/dx are raw deltas (one notch = 120)」 | ✅ 能 |

### 8.4 两方案（二选一 + 推荐）

| | 方案 ①：前台鼠标批 | 方案 ②：键通道等价物 |
|---|---|---|
| 改什么 | **零代码改动**（`--scenario t_rows` / `--scenario t_chips`，前台真鼠标） | 滚轮：**已实现**（`self.key("Next")`，无需改）；拖拽：**没有等价物**，要造就得改**靶子**（裂 `gym_app.py` 的 sha）⇒ 不做 |
